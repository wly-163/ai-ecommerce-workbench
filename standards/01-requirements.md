# 01 · 需求 / 活 PRD 〔本项目活记忆 · AI 维护〕

> **作用**:这是本项目唯一的需求文档。所有新功能、缺陷、技术债都追加到这里,不要另起多个 PRD 文件。
> **更新时机**:每次有新需求、需求变更、验收标准变化时更新。

---

## 1. 需求来源

| 类型 | 来源 | 进入方式 |
|---|---|---|
| 功能需求 Feature | 用户 / 老师 / 产品 / 客户 | 写成用户故事 |
| 缺陷 Bug | 测试 / 线上日志 / 用户反馈 | 写复现步骤和期望结果 |
| 技术债 Tech Debt | 开发 / Review / CI/CD 故障 | 写影响和修复目标 |

---

## 2. Issue 生命周期

| 阶段 | 状态 | 动作 |
|---|---|---|
| 提出 | Open | 写清场景、目标、验收标准 |
| 排期 | Backlog / Todo | 决定优先级和负责人 |
| 开发 | In Progress | 从 main 开 feature 分支 |
| 评审 | In Review | 提 PR,等待 CI 和 Review |
| 合并 | Done | PR 合并 main,自动关闭 Issue |
| 验收 | Verified | 按验收标准确认 |

**追踪规则**:分支名带 Issue 号,PR 描述写 `closes #<编号>`。

## 4. 需求清单

> 分阶段来源:`prd.md` 10 周计划。P0 优先,MVP 阶段(第 1–3 周)先交付。

### US-1 初始化项目工程化与 CI/PaaS CD · 状态: Backlog · 优先级: P0 · 第 1 周

作为 **项目开发者**,
我想要 项目具备基础工程结构、测试、CI 与 PaaS 自动部署,
以便 后续每次开发都能自动检查并发布到公网 Demo。

验收标准:
- AC1: 从 `main` 开 feature 分支完成初始化,不直接 push main。
- AC2: PR 触发 CI,至少包含格式检查、静态检查、单元测试、前端构建检查。
- AC3: CI 全绿后由人类合并 main。
- AC4: 合并 main 自动触发 CD — 前端部署到 **Vercel**,后端部署到 **Railway**;部署后 `GET /health` 返回 200。
- AC5: GitHub Secrets 已配置:`VERCEL_TOKEN`/`VERCEL_ORG_ID`/`VERCEL_PROJECT_ID`/`RAILWAY_TOKEN`(人类操作,AI 提示)。
- AC6: 本地 `docker-compose up` 可启动 postgres/redis/backend/frontend。
- AC7: 完成后更新 `standards/PROGRESS.md`。

技术备注:
- 无自有服务器,不使用 SSH CD 三件套。
- 本地不强制 Docker;CI 负责 `docker build` 兜底。

---

### US-2 项目骨架与 Docker 编排 · 状态: Backlog · 优先级: P0 · 第 1 周

作为 **项目开发者**,
我想要 前后端空项目与 Docker Compose 编排,
以便 一键启动完整开发环境。

验收标准:
- AC1: `frontend/` 为 Vite + React 19 + TypeScript,`pnpm dev` 可启动。
- AC2: `backend/` 为 FastAPI + Python 3.11,`GET /health` 返回 `{"status":"ok"}`。
- AC3: `docker-compose.yml` 编排 postgres、redis、backend、frontend 四个服务。
- AC4: 根目录有 `.env.example`,密钥不进 Git。
- AC5: 后端有至少 1 个 pytest 用例覆盖 `/health`。

---

### US-3 基础 LangGraph 工作流 · 状态: Done · 优先级: P0 · 第 2 周

作为 **运营人员**,
我想要 通过 API 调用一个最简单的 AI 工作流(输入→处理→输出),
以便 验证 LangGraph 编排链路可用。

验收标准:
- AC1: 定义 LangGraph State 与至少 2 个 Node(输入处理、LLM 输出)。
- AC2: `POST /api/v1/workflows/execute` 可执行工作流并返回结果。
- AC3: 支持 SSE 流式输出。
- AC4: 有单元测试覆盖工作流执行(可 mock LLM)。

---

### US-4 3D 场景 MVP · 状态: Backlog · 优先级: P0 · 第 3 周

作为 **管理者**,
我想要 在 3D 场景中查看代表商品的立方体并交互,
以便 直观感受数字孪生可视化能力。

验收标准:
- AC1: 使用 React Three Fiber 渲染 3D 场景,含 OrbitControls。
- AC2: 场景中至少 3 个不同颜色立方体代表不同品类。
- AC3: 前端调用后端 API,用返回结果改变立方体颜色。
- AC4: 场景可旋转/缩放,无明显性能问题(>30fps)。

---

### US-5 AI 智能导购 · 状态: Backlog · 优先级: P0 · 第 4 周

作为 **电商用户**,
我想要 用自然语言描述需求并获得个性化商品推荐,
以便 快速找到合适商品。

验收标准:
- AC1: Given 用户输入「推荐防晒衣」,When 发送聊天消息,Then 返回含商品名称与推荐理由的回复。
- AC2: RAG 双路召回(向量 + BM25) + Reranker 精排,Hit Rate ≥ 0.85(模拟测试集)。
- AC3: 支持多轮对话(追问、修改条件)。
- AC4: 前端有聊天界面(shadcn/ui)。

---

### US-6 智能客服 · 状态: Backlog · 优先级: P0 · 第 5 周

作为 **电商用户**,
我想要 查询订单状态和处理退换货问题,
以便 无需等待人工客服。

验收标准:
- AC1: Given 用户输入「查订单 xxx」,When 发送消息,Then 返回订单状态与物流信息。
- AC2: 意图路由区分售前/售后/意图不明,路由准确率 ≥ 90%(模拟测试集)。
- AC3: 售后政策 RAG 检索,回答含政策依据。
- AC4: 高风险请求(如大额退款)触发 Human-in-the-Loop,转人工审核。
- AC5: PostgreSQL 中有模拟订单数据。

### US-7 低代码工作流编辑器 · 状态: Backlog · 优先级: P0 · 第 6 周

作为 **运营人员**,
我想要 拖拽节点、连线并保存 AI 工作流,
以便 零代码配置业务自动化流程。

验收标准:
- AC1: React Flow 编辑器支持拖拽、连线、删除节点。
- AC2: 预置节点:Input、LLM、RAG、Condition、Output。
- AC3: 点击节点弹出配置面板。
- AC4: 工作流定义保存到后端 PostgreSQL,可 CRUD。
- AC5: 保存的工作流可通过 US-3 的执行接口运行。

### US-8 供应链智能预测 · 状态: Backlog · 优先级: P0 · 第 7 周

作为 **运营人员**,
我想要 看到销量预测、库存预警和补货建议,
以便 从经验驱动转向数据驱动补货。

验收标准:

- AC3: 自动生成差异化补货清单(商品、建议数量、理由)。
- AC4: Celery Beat 定时触发预测任务。

## 5. 非功能需求

- **安全**:密钥只进 GitHub Secrets / 环境变量,不进 Git。
- **可维护**:一需求一小 PR(<400 行),避免大爆炸式提交。
- **可测试**:核心逻辑必须有单元测试;后端覆盖率 ≥ 80%(核心模块),整体 ≥ 60%。
- **可部署**:PaaS 部署后 `/health` 必须通过;本地 `docker-compose up` 可复现。
- **可观测**:AI 决策链路可追踪,禁止黑盒。
- **Human-in-the-Loop**:退款审批、价格修改等高风险操作必须人工确认。
- **外部 API**:LLM/电商平台调用必须有重试机制与超时控制。
